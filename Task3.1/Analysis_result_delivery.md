# Доставка результатов анализов в мобильное приложение «Здоровье+»

## Описание решения

Результаты доставляет Сервис результатов анализов. Он забирает новые результаты из LIS инкрементальным опросом, сохраняет их в собственную витрину и публикует событие «Результат анализа готов» в брокер событий. Пуш-уведомление уходит пациенту только после того, как результат уже доступен для чтения, а приложение читает результаты из витрины, не обращаясь к LIS. Целевая задержка от готовности результата в LIS до появления в приложении — не более 1 минуты против текущих двух часов.

Сейчас LIS сама отправляет результаты в CRM по REST. После сбоя повторной отправки нет, файлы дублируются, лаборанты не видят состояния загрузки и не могут на неё повлиять. Изменять LIS нельзя, поэтому надёжность обеспечивается на стороне получателя.

### Как результат попадает в приложение

1. Сервис результатов анализов раз в 15–30 секунд запрашивает в LIS результаты, изменённые после сохранённой отметки времени. Окно запроса перекрывается с предыдущим, чтобы не пропустить записи, сохранённые в LIS с опозданием. Существующая отправка из LIS по REST перенаправляется в Сервис результатов и служит сигналом для внеочередного опроса: при работающей отправке задержка сокращается до секунд, а при её сбое результат всё равно будет забран при следующем опросе.
2. Каждый результат проходит проверку и сохраняется в витрину по ключу «идентификатор результата + версия». Повторно полученная версия игнорируется, новая версия (исправление лаборатории) заменяет предыдущую. Дубли устраняются на входе.
3. В той же транзакции, что и запись в витрину, событие сохраняется в исходящую таблицу (Transactional Outbox). Отметка опроса сдвигается только после фиксации транзакции.
4. Публикатор переносит события из исходящей таблицы в брокер событий. Ключ сообщения — идентификатор пациента, поэтому события одного пациента обрабатываются по порядку.
5. CRM и Уведомления читают событие независимо. Каждый потребитель идемпотентен и хранит идентификаторы обработанных событий. После исчерпания повторов сообщение уходит в очередь недоставленных сообщений.
6. Уведомления отправляют пуш без медицинских данных: «Результат анализа готов» и идентификатор результата.
7. Приложение запрашивает результат через API Gateway и BFF. Сервис результатов отдаёт его из витрины только владельцу после проверки токена.

### Гарантии доставки

- Ни один результат не теряется: отметка опроса сдвигается только после записи в витрину, а событие публикуется из той же транзакции. Каждый шаг выполняется «не менее одного раза».
- Ни один результат не дублируется: дедупликация в витрине и у каждого потребителя превращает «не менее одного раза» в «ровно один раз» с точки зрения пациента и врача.
- Пуш не приходит раньше результата: событие публикуется после записи в витрину.
- Ежедневная сверка сравнивает число результатов в LIS и в витрине за последние 48 часов. Расхождения показываются в Сервисе мониторинга и догружаются автоматически.

### Пиковая нагрузка

Нагрузка на LIS не зависит от числа пользователей приложения: её создаёт только опрос с постоянной частотой. Чтение 50 000 пользователей в часы пик обслуживает витрина: реплики PostgreSQL и кэш последних результатов пациента. Брокер событий сглаживает всплески, например утреннюю выгрузку ночных анализов: потребители обрабатывают очередь в своём темпе и масштабируются числом экземпляров в группе потребителей.

### Эксплуатация

- Консоль доставки для лаборантов и службы поддержки: статус каждого результата (получен из LIS, опубликован, доставлен в CRM, уведомление отправлено), ручная повторная публикация результата и повторная обработка очереди недоставленных сообщений.
- Метрики в Сервисе мониторинга: задержка от готовности в LIS до записи в витрину, отставание опроса, глубина очереди недоставленных сообщений, отставание потребителей. Оповещение — при задержке более 5 минут или недоступности LIS.
- Сквозная трассировка по идентификатору результата: от опроса LIS до открытия результата в приложении.

Загрузка данных с оборудования в LIS по FTP (ошибка 425) находится до точки готовности результата в LIS и в это решение не входит. Её надёжность требует отдельной доработки, но сбой на этом участке теперь будет виден: результат не появится в LIS, и это покажет сверка с лабораторным журналом заказов.

## Сравнение вариантов доставки

| Вариант | Гарантированная доставка | Задержка | Пиковая нагрузка | Простота эксплуатации | Изменения в LIS | Итог |
| --- | --- | --- | --- | --- | --- | --- |
| 1. Текущая схема: LIS отправляет результаты в CRM по REST, приложение читает из CRM | Нет: после сбоя повторной отправки нет, результаты теряются и дублируются | До 2 ч при сбоях | CRM выдержит чтение, но данные в ней неполные | Низкая: восстановление вручную, состояние загрузки не видно | Не нужны | Отклонён: причина текущих проблем |
| 2. Прямое чтение: приложение через BFF запрашивает результаты в LIS | Да, LIS — источник истины | Минимальная | Нет: каждый запрос пациента идёт в LIS, которая не масштабируется горизонтально | Средняя: нужна защита LIS от перегрузки | Не нужны | Отклонён: 50 000 пользователей перегрузят LIS |
| 3. Перехват изменений в БД LIS (CDC, Debezium) с публикацией в брокер | Да: журнал транзакций БД не теряет изменения | Секунды | Да: нагрузку на LIS создаёт только чтение журнала | Низкая: привязка к внутренней схеме БД LIS, доступ к журналу и поддержка поставщика под вопросом | Доступ к журналу транзакций, согласование с поставщиком | Отклонён: высокий риск при обновлениях LIS, тип СУБД и права доступа не подтверждены |
| 4. Только отправка из LIS (webhook) в Сервис результатов | Нет: LIS не повторяет отправку после сбоя (SD-005) | Секунды | Да | Средняя | Перенастройка адреса отправки | Отклонён как единственный механизм, используется как ускоритель в варианте 5 |
| 5. Инкрементальный опрос LIS Сервисом результатов анализов, витрина, Transactional Outbox, брокер событий; отправка из LIS — сигнал для внеочередного опроса | Да: отметка опроса сдвигается после фиксации, события из той же транзакции, дедупликация, сверка | Секунды при работающей отправке, до 30 с при опросе, цель — не более 1 мин | Да: нагрузка на LIS постоянна, чтение идёт из витрины, брокер сглаживает всплески | Высокая: консоль доставки, повторная публикация, очередь недоставленных сообщений, метрики задержки | Перенастройка адреса отправки (необязательно) | Выбран |
| 6. Пакетная выгрузка файлов из LIS по SFTP по расписанию | Частично: при контроле контрольных сумм и подтверждении приёма | Интервал выгрузки, обычно 15–60 мин | Да | Низкая: файлы, контроль полноты, ручной разбор ошибок | Настройка выгрузки | Отклонён: не обеспечивает задержку в минуты |

Выбран вариант 5: только он даёт гарантированную доставку без изменений в LIS и не переносит нагрузку пользователей на legacy-систему.

Вариант 3 стоит пересмотреть, если поставщик LIS подтвердит поддержку CDC и стабильность схемы БД: он сократит задержку до секунд без опроса. Архитектура при этом не меняется: CDC заменит только источник событий в Сервисе результатов анализов.

## Инструменты реализации

Инструменты выбраны так, чтобы опираться на уже используемый стек (Java, PostgreSQL, RabbitMQ) и на брокер событий из целевой архитектуры.

| Задача | Рассмотренные варианты | Выбор | Обоснование |
| --- | --- | --- | --- |
| Брокер событий между Сервисом результатов, CRM и Уведомлениями | Apache Kafka; RabbitMQ; прямые REST-вызовы потребителей | Apache Kafka | Хранит события заданный срок (не менее 7 дней) и позволяет перечитать их после сбоя потребителя. Независимые группы потребителей для CRM и Уведомлений, порядок по ключу пациента, масштабирование разделами. RabbitMQ удаляет сообщение после подтверждения и не даёт перечитать историю; прямые вызовы связывают доступность источника с доступностью каждого потребителя. |
| Витрина результатов | PostgreSQL; MongoDB; чтение из CRM | PostgreSQL с репликами чтения | Транзакция «запись в витрину + исходящая таблица» требует одной ACID-базы. PostgreSQL уже используется в Расписании и CRM, у команды есть опыт эксплуатации. Чтение из CRM смешало бы рабочую нагрузку CRM с чтением пациентов. |
| Кэш последних результатов | Redis; кэш в памяти экземпляра | Redis | Общий кэш для всех экземпляров Сервиса результатов, сбрасывается по событию о новой версии результата. Кэш в памяти расходится между экземплярами. |
| Публикация из исходящей таблицы в брокер | Debezium Outbox Event Router; собственный публикатор с опросом таблицы | Debezium Outbox Event Router | Читает журнал транзакций собственной базы Сервиса результатов, а не LIS, поэтому рисков варианта 3 нет. Задержка в доли секунды, нет нагрузки от опроса таблицы, готовая маршрутизация по типам событий. |
| Планировщик опроса LIS | Планировщик Spring с блокировкой ShedLock; Quartz; внешний планировщик заданий | Spring Scheduler + ShedLock | При нескольких экземплярах сервиса опрос выполняет только один, остальные — резерв. Решение не требует отдельной инфраструктуры и вписывается в Java-стек. |
| Повторы и очередь недоставленных сообщений | Повторы с нарастающей задержкой в потребителе + топик недоставленных сообщений в Kafka; только повторы | Повторы + топик недоставленных сообщений | Временные ошибки (недоступность CRM) устраняются повтором, постоянные (некорректные данные) не блокируют очередь и разбираются в консоли доставки. |
| Доставка уведомления на устройство | Пуш через FCM и APNs; SMS; электронная почта | Пуш через существующий сервис Уведомлений; SMS — резерв, если приложение не установлено | Пуш бесплатен и мгновенен. Медицинские данные в уведомление не включаются: оно только приглашает открыть приложение. |
| Наблюдаемость | OpenTelemetry + Сервис мониторинга; журналы каждого сервиса по отдельности | OpenTelemetry | Сквозная трассировка по идентификатору результата через опрос, брокер и потребителей; метрики отставания потребителей Kafka и задержки доставки. |
