# Базовые меры безопасности мобильного приложения «Здоровье+»

## Схема аутентификации

Пациент входит на нативном экране приложения по номеру телефона и одноразовому коду, а приложение получает токены OAuth 2.0 и передаёт короткоживущий токен доступа в заголовке Authorization: Bearer по TLS. Схема следует OAuth 2.0 for First-Party Applications (проект стандарта IETF для собственных приложений поставщика услуг) с PKCE (RFC 7636): пациент не покидает приложение, а токены, их хранение, ротация и отзыв устроены так же, как в стандартной схеме Authorization Code. Вариант с окном системного браузера (RFC 8252) не выбран, потому что приложение собственное, пароля нет, а единый вход с веб-порталом не требуется.

| Элемент | Решение |
| --- | --- |
| Протокол | OAuth 2.0 с выдачей ID-токена OpenID Connect; вход через точку Authorization Challenge из OAuth 2.0 for First-Party Applications, затем обмен кода авторизации на токены с PKCE (S256); поставщик — Сервис аутентификации |
| Форма входа | Нативный экран приложения: пациент вводит номер телефона и одноразовый код из SMS (действует 5 минут), не покидая приложение. Приложение не проверяет код само и не хранит его: проверку выполняет Сервис аутентификации |
| Защита входа | Ограничения на коды: не более 3 кодов на номер за 15 минут и 10 запросов кода с устройства за час (защита от рассылки SMS за счёт клиники), не более 5 попыток ввода кода, после чего попытка входа аннулируется (защита от перебора) |
| Токен доступа | JWT с подписью асимметричным ключом, срок жизни 10 минут, аудитория — API мобильного приложения; хранится только в памяти приложения |
| Токен обновления | Одноразовый, с ротацией при каждом использовании, срок 30 дней; хранится в Keychain (iOS) или Android Keystore. Повторное использование аннулированного токена отзывает всю сессию устройства |
| Передача токена | Только в заголовке Authorization: Bearer (RFC 6750) по TLS; никогда в адресе, параметрах запроса или журналах |
| Проверка токена | API Gateway проверяет подпись по ключам JWKS Сервиса аутентификации, издателя, аудиторию, срок и отзыв сессии. Идентификатор пациента берётся только из токена, и каждый сервис проверяет, что запрашиваемые данные принадлежат этому пациенту |
| Выход и отзыв | Отзыв токена обновления (RFC 7009) при выходе или по заявке при утере устройства; API Gateway сразу перестаёт принимать токены отозванной сессии |

Схема закрывает риск подмены сессии (SD-007): токен короткоживущий и привязан к пациенту, идентификатор пациента нельзя подставить в запрос, а украденный токен обновления обнаруживается при повторном использовании. Следующий шаг — привязка токенов к ключу устройства по DPoP (RFC 9449), чтобы украденный токен нельзя было использовать с другого устройства.

Проверка подлинности приложения и устройства (аттестация) в этом документе не рассматривается и прорабатывается отдельно.

## Политика rate limiting

Лимиты применяет API Gateway по алгоритму «маркерная корзина» (token bucket) с общим счётчиком для всех его экземпляров. Публичный запрос ограничивается по устройству и IP-адресу, авторизованный — по пациенту из токена.

| Тип запроса | Лимит | Действие при превышении |
| --- | --- | --- |
| Поиск врачей (публичный, без аутентификации) | 30 запросов в минуту с одного устройства (идентификатор установки приложения) с кратковременным всплеском до 10 запросов; 300 запросов в минуту с одного IP-адреса — с запасом на мобильные сети, где много пользователей выходят с одного адреса | Ответ 429 Too Many Requests с заголовком Retry-After; приложение показывает последние результаты из своего кэша. Если с одного IP-адреса лимит превышен 5 раз за 10 минут, адрес блокируется на 15 минут и событие уходит в Сервис мониторинга: это признак автоматического сбора справочника врачей. |
| Создание записи к врачу (авторизованный) | 5 запросов в минуту и 20 в сутки на одного пациента (идентификатор из токена); не более 3 одновременных записей в статусе «ожидает оплаты». Повтор с тем же ключом идемпотентности в лимит не засчитывается | Ответ 429 с Retry-After и понятным сообщением в формате Problem Details; новая запись не создаётся и слот не резервируется. При превышении суточного лимита или лимита неоплаченных записей пациенту предлагается оплатить или отменить уже созданные; событие уходит в Сервис мониторинга для проверки на захват слотов. |

Лимиты — стартовые и уточняются по фактическому поведению пациентов после запуска. Оба запроса дополнительно защищены общим лимитом на метод, рассчитанным по нагрузочному тесту: он не даёт всплеску трафика перегрузить Расписание.

## Меры защиты каналов передачи данных

Каждый канал, по которому идут персональные и медицинские данные, шифруется и аутентифицирует обе стороны там, где это возможно. Меры обязательны для запуска MVP.

1. TLS 1.3 на всех внешних каналах между приложением, API Gateway и Сервисом аутентификации; TLS 1.2 допускается только с наборами шифров с прямой секретностью. Незащищённый HTTP отключён, в приложении запрещены нешифрованные соединения.
2. Закрепление открытого ключа сертификата (certificate pinning) в приложении для адресов API Gateway и Сервиса аутентификации, с резервным ключом для смены сертификата. Защищает от перехвата через поддельный или установленный вручную корневой сертификат.
3. Взаимная аутентификация внутренних сервисов (mTLS) через сервисную сетку с автоматической ротацией сертификатов: данные шифруются и внутри контура, а сервис принимает вызовы только от разрешённых сервисов.
4. Шифрование и аутентификация клиентов брокера событий (TLS, списки доступа к топикам) и каналов к 1С, LIS и платёжному шлюзу (TLS, mTLS при поддержке поставщиком).
5. Проверка подлинности уведомлений от платёжного шлюза: подпись сообщения и список разрешённых адресов отправителя. Иначе поддельное уведомление может подтвердить запись без оплаты.
6. Никаких персональных данных и токенов в адресе запроса: идентификатор пациента берётся из токена, токен — только в заголовке. Адреса запросов попадают в журналы прокси и балансировщиков.
7. Маскирование персональных и медицинских данных в журналах и трассировках всех систем, включая Сервис мониторинга.
8. Запрет кэширования ответов с медицинскими данными на промежуточных узлах и в системном кэше телефона (Cache-Control: private, no-store); локальные данные приложения хранятся в зашифрованном виде.
9. Пуш-уведомления и SMS без медицинских данных: они проходят через внешних провайдеров и видны на заблокированном экране, поэтому только приглашают открыть приложение.
10. Проверка входящих запросов на API Gateway по контракту OpenAPI и межсетевой экран для веб-приложений (WAF): запросы с лишними полями, неверными типами и признаками инъекций отклоняются до сервисов. Это дополнение, а не замена параметризованных запросов к базам данных в сервисах (INT-006).

Медицинские данные относятся к специальной категории персональных данных по 152-ФЗ. Уровень защищённости и необходимость сертифицированных средств криптографической защиты (TLS на алгоритмах ГОСТ) нужно определить со службой информационной безопасности до запуска.
